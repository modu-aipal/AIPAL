## 1. 기술 스택

| 구분 | 사용 | 비고 |
|---|---|---|
| 화면 | HTML + CSS + 바닐라 JS, `dashboard/index.html` 한 파일 | 약 776KB, 데이터·펄이 이미지 내장 |
| 3D | three.js r128 (cdnjs) + 예제 모듈(EffectComposer·UnrealBloomPass·GLTFLoader, jsdelivr `three@0.128.0`) | 버전 고정 |
| 차트 | SVG 직접 그리기 (추이·막대·히트맵) | 차트 라이브러리 없음 |
| 글꼴 | Google Fonts: Black Han Sans, IBM Plex Sans KR, IBM Plex Mono | |
| 앱 설치 | `manifest.webmanifest` + `sw.js` (서비스 워커) | |
| 데이터 준비 | Python 3 표준 라이브러리 (`embed_data.py`, `build_stores.py`) | pandas 불필요 |
| 3D 모델 | Blender (`pearl/pearl_robot.blend` → `pearl.glb`, 표정 webp) | 페이지에는 base64로 내장 |
| 배포 | Vercel 정적 호스팅 + 서버 함수 2개 (Root Directory = `dashboard`) | 프로젝트 `aipal-sangkwon-pulse` |
| B 프록시 | Vercel Functions (Node, `dashboard/api/`), `vercel.json` | PR #13 예시를 그대로 복사 (PR #17) |
| 3D 자원 (병합 전) | Blender 5.1 (Cycles, 백그라운드 `-b --factory-startup`), Python 스크립트 | 위성사진·AO·건물·나무·탑 모델을 미리 만들어 파일로 둠 |

### 1.1 의도적으로 쓰지 않는 것

| 쓰지 않는 것 | 이유 |
|---|---|
| 빌드 도구·프레임워크 (React, Vite 등) | 파일 하나로 열고 배포. 팀원 누구나 `http.server`로 바로 확인 |
| 대시보드 서버·DB | 공개 데이터만 보여 줌. 저장할 사용자 데이터 없음 (서버 함수는 B 전달만 함) |
| 외부 지도 API (키 필요) | 키 관리 부담. 지형은 공개 타일로 미리 만들어 내장 |
| 페이지 안 API 키 | 페이지에 넣으면 누구나 볼 수 있음 → Vercel 환경변수 `B_API_KEY`에 두고 서버 함수가 붙임 |

## 2. 시스템 구성

```
                 ┌──────────── 빌드 시점 (사람이 실행) ────────────┐
C: calc_engine/data/dashboard_data.json ─┐                          │
C: calc_engine/data/dashboard_data_extra.json ─┼─ embed_data.py ─→ index.html (const DATA_META / AREAS / EXTRA)
소상공인 상가정보 CSV + data/area_map.csv ─── build_stores.py ─→ dashboard/stores/{area_id}.json
                 └──────────────────────────────────────────────────┘

                 ┌──────────── 실행 시점 (브라우저) ────────────────┐
index.html ─ 내장 데이터로 지도·순위·리포트·히트맵·말풍선 답
          ├─ stores/{id}.json   (상권을 열 때만 fetch, 서비스 워커가 저장)
          └─ 같은 주소 /health · /api/dashboard/analyze (meta "self")
               └─ Vercel 서버 함수(api/health.js · api/dashboard/analyze.js): X-API-Key 붙여 B_API_URL 로 전달 → B
sw.js     ─ 화면·three.js·글꼴·3D 자원 저장 (같은 주소 /api*·/health 와 B 요청은 건드리지 않음)
                 └──────────────────────────────────────────────────┘
```

### 2.1 핵심 설계 원칙

1. **숫자는 C 파일 그대로.** 대시보드는 비중·순위 정렬·반올림 같은 표시 계산만 한다.
2. **B가 없어도 화면은 완성된다.** B는 직접 입력 질문에만 쓴다.
3. **B 답변은 글자로만 넣는다.** HTML로 해석하지 않는다 (`esc()` 후 줄바꿈만 `<br>`).
4. **B·C 파일은 수정하지 않는다.** 필요하면 요청·제안 PR로 남긴다.

## 4. 데이터

### 4.1 내장 데이터 (`embed_data.py`)

| 입력 | 출력 (`index.html` 안의 줄) |
|---|---|
| `calc_engine/data/dashboard_data.json` (리포트 20곳) | `const DATA_META=`, `const AREAS=` |
| `calc_engine/data/dashboard_data_extra.json` (지도 80곳) | `const EXTRA=`, `const EXTRA_QUARTERS=` |

- 숫자는 C 파일 그대로. 지도 좌표(`pos`)와 구 이름(`gu`)만 대시보드 값을 `id`로 붙인다.
- `--check`: 바뀔 내용만 출력. **2026-11-23 main 기준 "바뀐 내용 없음"** (리포트 20곳 26Q2, 지도 80곳 24Q3–26Q2).
- 단위: 매출 억 원(소수 1자리), 점포당 매출은 분기 합계 ÷ 3 월평균, 객단가 원, 비율 %.
- `DATA_META.notes`: 추정매출 안내, 분기 3개월 합계, 점포 수에 프랜차이즈 포함, 성별·연령 합계에 법인 매출 빠짐.

### 4.2 상권 ↔ 행정동 (`data/area_map.csv`)

대시보드 20곳(`area_id`)이 합친 행정동 코드(`dong_code`, OA-22175의 8자리 `행정동_코드`) 목록. 성수는 4개 동 등 여러 동을 합친 곳이 있다. 신사동은 서울에 두 곳이라 코드(강남구 `11680510`)로 구분한다.

### 4.3 가게 검색 데이터 (`build_stores.py`)

| 항목 | 내용 |
|---|---|
| 원본 | 공공데이터포털 15083033 소상공인 상가(상권)정보, 서울 CSV (UTF-8, 약 300MB, git 제외) |
| 연결 | 원본의 `행정동코드`(8자리) = `area_map.csv`의 `dong_code` → 23개 동 모두 일치 |
| 출력 | `dashboard/stores/{area_id}.json` 20개, 99,735곳, 합계 9.4MB (가장 큰 강남 gzip 약 280KB) |
| 형식 | `{area, source, asof, dongs, cats, cols, rows}`. `cols` = 상호·업종·층·건물·도로명주소·동·경도·위도, 업종·동은 번호로 가리켜 크기를 줄임 |
| 안전장치 | 가게가 0곳인 상권이 있으면 중단 (행정동 코드 변경 감지) |

## 5. 3D 지도

### 5.1 지도와 데이터 탑

| 항목 | 구현 |
|---|---|
| 지형 | AWS Terrain Tiles(SRTM 기반) 표고를 미리 받아 내장, 높이 4배 강조. 낮은 지대에서 한강 추출 |
| 위치 | 행정동 경계(vuski/admdongkor ver20251231)의 면적 중심 |
| 큰 건물 | 상권 100곳. 높이 = 선택한 시간대 매출 (땅 높이와 더하지 않음). 굵은 탑 = 리포트 20곳, 가는 탑 = 지도 80곳 |
| 색 | 시장·도매형 보라, 선택 상권 네온핑크, 소비·서비스형 파랑 |
| 작은 건물 | 배경 장식 (데이터 아님) |
| 조작 | 끌어서 돌리기, 확대·축소, 상권 클릭 → 선택 |
| 시간대 | 6구간 (00–06 심야, 06–11 아침, 11–14 점심, 14–17 오후, 17–21 저녁, 21–24 밤), 재생 시 자동 전환 |

### 5.2 도시 비주얼 (브랜치 `a/seoul-visual`, 병합 전)

보기용 자원은 모두 **미리 만들어 파일로 두고**, 페이지는 불러와 입히기만 한다. 데이터 탑의 높이(매출)·색(1위 업종 유형)·선택 강조는 그대로다.

| 항목 | 파일 | 만드는 법 | 화면 |
|---|---|---|---|
| 낮 지면 | `satellite.jpg`(데스크톱) · `satellite-sm.jpg`(폰) | Sentinel-2 L2A 2026-05-31 참값 컬러를 지도 범위로 자름 (`fetch_satellite.py`) | 낮에 지형 위에 입힘, 밤은 예전 지면 |
| 지면 그늘(AO) | `ao.jpg` · `ao-sm.jpg` | 지형·건물을 Blender Cycles로 AO bake (`bake_ao.py`, `finish_ao.py`: 흐림·건물 주변만 가까운 그늘) | 낮 지면에 곱함 |
| 실제 건물 | `buildings.bin` | OpenStreetMap 건물 윤곽·높이(층수) 추출 (`extract_buildings.py`) | 데스크톱만. 높이 40m↑ 사무실 / 15–40m 콘크리트 / 그 밖 벽돌 외벽 |
| 외벽 사진 | `tex/facade-{glass,office,brick,concrete}.jpg` | ambientCG CC0 | 낮에만 섞임(`uFacadeMix`), 밤은 창문 불빛 |
| 나무 | `trees.bin` · `tex/trees.webp` | Poly Haven CC0 나무를 Blender로 그림처럼 구움(`render_trees.py`), 위성사진 초록(2G−R−B > 30) 자리, 리포트 20곳 주변(`gen_trees.py`) | 낮에만, 폰은 1/3 |
| 데이터 탑 건물 | `models/tower-{base,mid,roof}.glb` | 유진아 Meshy 모델 → Blender: 붙이기 → voxel remesh 0.012 → 줄이기 → UV 새로 펴기 → 원본 색 bake (`process_tower_kit.py`). 각 약 0.5–0.7MB | 낮·밤 같은 건물. 아랫부분·꼭대기는 크기 고정, **몸통을 쌓는 개수로 높이 = 매출**. 밤: 유리(푸른 부분)에만 창문 불빛, 꼭대기는 유형 색 빛 |

- 폰(`weak`): 작은 위성사진·AO, OSM 건물 없음, 나무 1/3, 건물 모델은 리포트 20곳만 (지도 80곳은 예전 네온 기둥).
- 용량: 데스크톱 약 7MB, 폰 약 3MB (서비스 워커가 저장).
- 만드는 스크립트는 지금 외장 드라이브(`aipal-seoul-data/scripts/`)에만 있다 → 저장소에 넣을지 미정 (PRD Q-07).
- 셰이더: three.js r128 `onBeforeCompile`로 주입. 같은 셰이더 코드를 쓰는 재질은 프로그램을 공유하므로 재질마다 다른 값은 uniform으로만 넘긴다.

### 5.3 데이터 탑 건물 5종 (계획)

- 유진아 Meshy 모델 5세트(지금 1세트 + 4세트 제작 중)를 탑마다 **골고루 섞음** (옆 탑끼리 같은 건물 피함). 건물 모양은 데이터 의미가 없다.
- 모델 기준: 바닥 정사각형·네 면 비슷하게, 유리는 푸른빛(밤 창문 불빛 조건), 글자 간판 없음, 실사풍 통일. 몸통은 위아래가 같아 쌓아도 이음새가 안 보이게(높이 ≈ 폭 2.5배), 아랫부분 ≈ 1:1, 꼭대기 ≈ 폭 1.7배로 실루엣을 다르게.
- 밤 밝기는 지금(`pulse-v14`) 수준 유지 — 층마다 네온 띠·모서리 네온을 더한 버전은 너무 밝아 되돌림 (11/24).

## 6. 펄이와 B 연동

### 6.1 질문 경로

| 질문 | 경로 |
|---|---|
| 말풍선 질문 5개 (매출 1위 상권, 성수 카페, 주말 비중, 1년 성장, 밤 9시 이후) | API 없이 내장 데이터로 즉시 답. 카페 답에는 C `cafe_store`의 카페 점포 수·한 곳당 월매출 (PR #21; 카페 0곳이면 문장 생략, 매출이 없으면 점포 수만) |
| 직접 입력, 나온 상권이 **모두** B 지원 지역 | `POST {API}/api/dashboard/analyze` |
| 직접 입력, B 지원 지역 밖 상권 포함 (지도 80곳 등) | 내장 데이터로 답 + "AI 분석 서버는 ○곳만 계산할 수 있어서 대시보드 데이터로 답했어요" |

- B 지원 지역은 페이지를 열 때 `GET /health`의 `regions`로 받는다 (지금 20곳). `regions`가 없는 예전 B면 5곳(성수·홍대·건대·강남·이태원)으로 본다.
- 상권 이름 찾기: 지도 100곳 이름 + "동" 뺀 이름 + 별칭, 긴 이름 먼저.
- 업종 찾기: 데이터 업종 62개(`IND_ALL`, **부동산중개업 빠짐** — FINAL_CHECKLIST F1 #7) + 별칭(`IND_ALIAS`: 성형외과·피부과·안과·내과·병원 → 일반의원, 카페·커피 → 커피-음료, 술집·호프 → 호프-간이주점 등).

### 6.2 요청

```
POST {API}/api/dashboard/analyze        ← 기본 {API} = 페이지 주소(self) → Vercel 서버 함수 → B
Content-Type: application/json
ngrok-skip-browser-warning: 1        ← ngrok 무료 도메인 경고 페이지 건너뛰기
{"question": "<사용자 입력>"}
```

- 시간 제한 150초 (`AbortController`). 로컬 모델이라 수십 초 걸릴 수 있다는 안내를 기다리는 동안 표시.
- 페이지는 API 키 헤더를 보내지 않는다. B가 `X-API-Key`를 요구하게 되어(11/23) 서버 함수가 `B_API_KEY`를 붙인다 (PR #17). 함수 시간 제한 150초(`vercel.json`).
- `?api=<B 주소>`로 B에 직접 보내면 키가 없어 401 → 내장 데이터로 답한다.

### 6.3 응답 처리

| B 응답 | 화면 |
|---|---|
| 200 `{area, sql, text}` | "AI 분석 서버" 배지 + `text`(글자 그대로, 줄바꿈만 `<br>`), `area` 상권으로 지도 이동(`geondae` → `kondae`), "실행한 SQL 보기"(비면 "SQL 없이(pandas) 계산") |
| 200 + Mock | "테스트용 Mock 데이터 · 실제 분석 결과 아님" 배지 (헤더 `X-Is-Mock` 또는 `text` 접두어) |
| 422 `needs_clarification` | 대시보드 안내 문구 + 예시 질문 버튼("{지역} {업종} 분기별 매출 추이 보여줘", 질문의 지역·업종으로 채움) + "서버 원문" 접기 |
| 401 / 5xx / 연결 실패 / 150초 초과 | 사유 표시, 상단 상태 "AI 분석 서버에 연결할 수 없어요 · 대시보드 데이터로 답해요", 내장 데이터로 답할 수 있으면 답 |

- B의 `reason`·`suggested_questions`는 아직 쓰지 않는다 (PRD Q-02, B와 협의 중).
- 진행 단계 표시: 질문 해석 → SQL 실행 → 상권 이동 → 해석 작성.

### 6.4 펄이 3D

데스크톱은 glb 3D(마우스를 따라 고개, 깜빡임, 생각 중 눈 굴리기, 말할 때 입), 폰·느린 기기·동작 줄이기 설정은 표정 이미지 4장. 끌어서 위치를 옮길 수 있다 (PR #6).

## 2. 시스템 구성

```
A (Vercel 서버 함수: X-API-Key 부착)
      │  POST /api/dashboard/analyze {question, history}
      ▼
B  app/api/routes/dashboard.py
   ├─ core/security.py        X-API-Key 검증 (/health 제외)
   ├─ services/planner.py     질문 → AnalysisPlan (모델 초안 + 규칙 검증)
   │    ├─ understand.py, metrics.py, periods.py, areas.py, dataset.py   (지역·업종·기간·지표 읽기)
   │    ├─ composition.py, judgment.py, data_facts.py, follow_up.py      (특수 질문 유형)
   │    └─ ollama.py          모델 호출 (30초/400토큰, 실패하면 건너뜀)
   ├─ services/calc/          build_request → C /calculate → verify_result
   ├─ services/ranking.py     순위·하한·표시용 정렬
   ├─ services/answer_extras.py  창업·수입: 같은 조건 순위, 이어 물어볼 질문
   └─ services/compose.py · explain.py   답변 문장 구성 {area, sql, text}
      │
      ▼
C  POST /calculate (8100)
```

### 2.1 핵심 설계 원칙

1. **숫자는 C에서만.** B는 단위·반올림 같은 표시 변환만 한다.
2. **코드 값이 모델 값을 이긴다.** `evaluate(question, draft, ...)`는 순수 함수이고 모델 없이도 같은 규칙으로 동작한다.
3. **애매하면 이어받지 않고 되묻는다.** 엉뚱한 조건이 붙는 것보다 안전하다.
4. **안내한 질문은 반드시 통과해야 한다.** 제안 질문은 서버가 직접 `evaluate`로 확인(`verify_questions`)한 것만 보여 준다.
5. **A·C 파일은 수정하지 않는다.** 필요한 것은 이슈·PR 문서로 요청한다 (이슈 #26: A의 `history` 전송).

## 4. 질문 해석 (`planner.evaluate`)

### 4.1 순서

1. 이어 묻기 판별 (`follow_up.is_follow_up`) → 직전 질문에서 **빠진 조건만** 상속 (`build_context`).
2. 모델 초안(`PlanDraft`)을 받는다 (시간 초과면 건너뛰고 규칙만으로 진행, Ollama가 꺼져 있으면 오류 503).
3. 특수 질문 순서로 규칙 검사: 구성비 → 생존·위험 → 전망 → 수입 → 비교 → 위치 → 창업 → 경쟁.
4. 지역·업종·기간·지표를 규칙으로 읽는다. 읽은 값이 모델 값보다 우선.
5. 기간 범위(2021Q1 ~ 최신 분기) 검사, 필수 조건이 빠지면 되묻기.
6. `AnalysisPlan`(조회·순위·비교·추이 등) 확정.

### 4.2 주요 규칙

| 항목 | 규칙 |
|---|---|
| 점포당 | 점포·가게·매장·업소 + 당·별·마다·하나당·대비·나눠, "가게 평균 매출" (`metrics.is_per_store`) |
| 합계 | "합계·총" 표현이면 합계 (`TOTAL_WORDS`) |
| 전년 대비 | `YOY_RE` → 증감 지표를 넣고 `growth_basis="year_over_year"`, 기준 기간을 요청에 명시 |
| 판단 표현 | startup·survival·danger·income·outlook·compare·invest·success (`judgment.py`), 위험 표현은 "유망·희망"을 제외 |
| 구성비 | 주중·주말·요일·성별·연령·시간대 등 (`composition.py`), 여러 항을 한꺼번에 읽음 |
| 데이터 설명 | 13개 주제 (`data_facts.py`), 분석어(매출·순위·점포 수…)가 있고 묻는 말(뭐·언제·어디·왜…)이 없으면 건너뜀 |
| 이어 묻기 | 이어 묻는 표현이 있고 새 질문에 조건이 빠졌고 그 질문 유형이 필요로 할 때만. 생략형은 ≤14자·≤2어절 |
| 업종 별칭 | 부동산·공인중개사→부동산중개업, 한식→한식음식점, 치킨, 빵집·베이커리, 피시방, 헬스장 등 |
| 야간 | '야간'·'21시~06시'는 밤(21~24시)과 새벽(0~6시) **두 칸의 합**. 두 칸을 C에 각각 요청하고 서버가 C 값 두 개를 더해 표시(`combine.py`), 답에는 합계와 두 값을 함께 보여 준다. '밤'은 21~24시, '새벽·심야'는 0~6시 |
| 합계의 N곳 | '성수 홍대 강남 이태원 건대 5곳 전체 매출 합계'의 5곳은 상위 5개가 아니라 말한 지역의 수라서 합산 값 하나로 답한다. 이름 없이 '5곳 합계'면 상위 5곳 순위 |
| 모델이 되읽은 말 | 모델이 '없는 항목'이라고 되읽은 말이라도 질문 속 기간·지역·업종·지표 표현(예: '2025년 4분기 매출')이면 규칙이 이해하므로 무시한다. 정말 없는 항목(유동인구·임대료)만 막는다 |

### 4.3 순위 하한 (`ranking.py`)

| 순위 종류 | 조건 | 이유 |
|---|---|---|
| 증감률·점포당 | 매출 합계 1억 원 이상 그룹만 | 매출이 작으면 값이 크게 흔들림 |
| 개업률·폐업률 | 점포 평균 30개 이상, 매출 0 초과 | 표본이 작으면 비율이 왜곡 |

제외한 사실은 답변에 밝힌다.

# C 계산 엔진 · 데이터 — 기술 명세

> 담당 C 이성균. 기준: 2026-11-24 팀 레포 `main`.

## 1. 기술 스택
| 구분 | 사용 기술 | 고른 이유 |
|---|---|---|
| 계산 API | Python, FastAPI (`POST /calculate`, `GET /health`, 포트 8100) | B 서버와 같은 언어·프레임워크라 연결과 테스트가 쉬움 |
| 계산 | pandas | 분기·지역·업종 집계를 짧고 검증 가능한 코드로 씀 |
| 테스트 | pytest, FastAPI TestClient | 서버를 띄우지 않고 요청·응답까지 확인 |
| 데이터 | 서울 열린데이터광장 CSV (아래 5절) | 공공기관 데이터, 이용 제한 없음 |

### 1.1 의도적으로 쓰지 않는 것
| 쓰지 않는 것 | 이유 |
|---|---|
| LLM이 숫자를 계산하거나 고치게 하는 것 | 숫자는 계산 엔진에서만 나와야 근거를 댈 수 있음 |

## 2. 위치 (전체 흐름 속 C)
```
사용자 질문 → A 대시보드 → B 분석 서버(질문 해석·계획) → C 계산 엔진(숫자) → B(답변 문장) → A(화면)
```
- B는 계획(어떤 지표를, 어떤 조건으로, 어떤 연산으로)만 만들고, **숫자는 C만 만든다.**
- 대시보드에 미리 넣어 둔 숫자(리포트·지도·말풍선 답변)도 C가 만든 데이터 파일에서 나온다 (4절).

## 3. 계산 엔진
### 3.1 허용 연산
| op | 계산 | 비고 |
|---|---|---|
| `sum` | 합계 | |
| `avg` | 분기당 평균 = 기간 합계 ÷ 기간 내 분기 수 | 점포 수처럼 "쌓인 값"은 여러 분기를 물으면 이것으로 |
| `growth_rate` | 증감률 = (현재 − 기준) ÷ 기준 | 기준 값이 0이거나 없으면 `null` + 사유(`baseline_zero` / `baseline_missing`) |
| `ratio` | 비율 = 합계 ÷ 다른 합계 (예: 주말 매출 ÷ 총매출, 폐업 수 ÷ 전체 점포 수) | 성별·연령은 법인 매출이 빠진 합계로 나눔 |
| `share` | 전체 중 비중 | |
| `per_store` | 점포당 월평균 = 매출 ÷ (전체 점포 수 × 3개월) | 상권분석서비스 사이트와 같은 정의. 업종 조건도 함께 쓸 수 있음 |

### 3.2 검사 · 오류 규칙
| 코드 | 언제 |
|---|---|
| `COLUMN_NOT_FOUND` | 없는 지표·컬럼을 요청 |
| `UNSUPPORTED_OPERATION` | 허용 안 된 연산, 또는 그 지표에 쓸 수 없는 연산 (예: 점포 수에 `per_store`) |
| `INVALID_REQUEST` | 기간 형식이 틀리거나 분기 경계가 아님, 규격에 안 맞는 요청 |
| `NO_DATA` | 조건에 맞는 데이터가 없음 (예: 2030년) |
| `DATASET_NOT_FOUND` | 없는 데이터셋 |
| `INTERNAL_ERROR` | 예상하지 못한 오류 (숫자를 내지 않음) |

### 3.3 응답에 함께 담는 것
숫자만 주지 않고 **어떻게 나왔는지**를 함께 준다. B는 이것으로 답변의 근거와 주의 문구를 만든다.
- 적용 조건, 연산별 계산식(`methods[].formula`), 사용한 행 수, 데이터 출처·버전
- 안내(notes): 분기 단위로 계산함, 성별·연령은 법인 매출 제외, 업종 묶음 펼침(예: 카페=커피-음료), 지역에 포함된 동 개수, 점포 수는 프랜차이즈 포함

### 3.4 매출 표와 점포 표를 합치는 방법
두 표를 행끼리 붙이지 않고, **같은 조건(지역·분기·업종)으로 각각 집계한 뒤 나눈다.** 그래서 키가 겹쳐 행이 불어나는 문제가 생기지 않는다.
