# 대시보드(A) 연동 API

## `POST /api/dashboard/analyze`

질문 → 의미 해석(펄이) → 분석 계획 → 계산 엔진(C) → 구조화된 답변 → `{area, sql, text}`

요청

```json
{"question": "가산동에서 잘나가는 업종"}
```

응답 200 (본문은 3개 필드로 고정)

```json
{
  "area": "gasan",
  "sql": "",
  "text": "가산동의 업종 중 매출 규모 상위 5개 업종입니다 (전체 55개 중, 2025Q3~2026Q2).\n1. 일반의류 — 매출 20,146.7억 원 · 증감 -0.4% · 점포당 월 16,606만 원\n2. …\n\n→ 증감은 목록 5개 중 1개가 늘고 4개가 줄었습니다.\n→ 매출 1위 일반의류는 증감이 -0.4%로, 규모는 크지만 줄고 있습니다.\n\n※ 기준: 기간: 최근 4분기(2025Q3~2026Q2)"
}
```

| 필드 | 규칙 |
|---|---|
| `area` | 지역 식별값. **`data/area_map.csv`의 `area_id`와 같다**(대시보드 `AREAS`의 `id`). 20곳: `jegi nr2 gasan hangang jongno gangnam garak hongdae nr1 yeouido apgu seongsu cheongdam sinsa ydp myeong doksan nonhyeon kondae itaewon`. 복수 지역은 쉼표 연결(`"seongsu,hongdae"`), 전체 순위·업종 비교처럼 지역을 지정하지 않으면 `""` |
| `sql` | 계산 엔진이 `executed_sql`로 **실제 실행한 SQL을 보고했을 때만** 그 값. Pandas 계산이면 `""`. B는 SQL을 생성·실행하지 않음 |
| `text` | 아래 구조. **줄바꿈(`\n`)이 구조를 만든다.** 대시보드가 `\n`을 `<br>`로 바꿔 주므로 A 수정 없이 그대로 보인다 |

## 답변 구조 (`text`)

문단 사이는 빈 줄(`\n\n`)이다.

| 문단 | 내용 | 누가 만드나 |
|---|---|---|
| ① 결론 + 목록 | 결론 한 줄 + 번호/점 목록. 숫자는 계산 결과에서 그대로, 순위는 정렬한 순서 | **코드** |
| ② 관찰 (`→`) | "증감은 목록 5개 중 1개가 늘고 4개가 줄었습니다", "매출 1위 X는 증감이 -0.4%로, 규모는 크지만 줄고 있습니다", 추이의 가장 높은·낮은 분기 | **코드** (계산 결과에서 직접 뽑음) |
| ③ 모델 해석 | 1~2문장. **기본은 꺼짐**(`EXPLAIN_INTERPRETATION=true`로 켬). 숫자·추천·"없다"·목록 재나열을 검사하고 실패하면 뺀다 | 모델 (옵션) |
| ④ 기준·주의 (`※`) | 가정(업종·기간), 제외 안내, 엔진 notes, 시장·도매형 등 지역 주의 | **코드** |

- 모델 해석을 기본으로 끈 이유: 숫자·추천·"없다"만 검사해서 "A가 다른 업종보다 규모가 크다" 같은 **틀린 비교**가 통과할 수 있었다. 코드가 만든 관찰은 항상 맞다.
- 값 하나를 묻는 질문("강남 매출 알려줘")은 결론 한 줄이 곧 답이다.
- 목록 형식: 순위 질문 `1. 청과상 — 매출 31,447.3억 원 · 증감 +18.9% · 점포당 월 35,176만 원`, 비교·추이 `• 성수 — …`. 표시 규칙은 `docs/DATA.md` 6절(억 원 소수 첫째 자리, 증감 부호 %, 점포당 월평균 만 원).

## 질문 유형 (펄이가 해석)

| 유형 | 예 | 처리 |
|---|---|---|
| 단일 조회 | "강남 매출 알려줘", "성수 요즘 장사 어때?" | 지역 1곳. "장사 어때·잘돼"는 규모·증감·점포당 세 가지를 함께 보여 줌 |
| 지역 비교 | "성수와 홍대 중 어디가 더 잘돼?" | 지역 2곳 이상, 기준 지표 순 |
| 업종 비교·순위 | "가산동에서 잘나가는 업종", "강남 요즘 뜨는 업종" | 업종별 계산 후 **코드가 정렬, 상위 5개**(TOP N을 말하면 N개) |
| 분기별 추이 | "홍대 카페 분기별 매출 변화" | 분기별 값 |
| 상권 순위 | "요즘 뜨는 상권은?", "장사 잘되는 곳 TOP 3" | 20곳 전체를 계산해 코드가 정렬 |

### "잘나가는·뜨는" 같은 말은 어떻게 이해하나
사람이 돌려 말한 표현을 **개념(concept)** 으로 바꾸고, 코드가 개념을 데이터의 지표로 바꾼다.

| 개념 | 표현 예 | 정렬 기준 | 함께 보여 주는 값 |
|---|---|---|---|
| overall | 잘나가는, 장사 잘되는, 인기, 돈 되는 | 매출 규모 | 증감 · 점포당 월평균 |
| growth | 뜨는, 핫한, 성장, 늘어난 | 매출 증가율 | 매출 · 점포당 |
| size | 매출 높은·큰 | 매출 규모 | 증감 · 점포당 |
| efficiency | 점포당, 한 달에 얼마 버는 | 점포당 월평균 | 매출 · 증감 |
| count | 점포 몇 개 | 점포 수(분기 평균) | — |
| closures / openings | 폐업·문 닫는 / 개업·새로 문 연 | 폐업·개업 수 | — |

- 방향: 낮은·안 되는·하위 → 오름차순. "많은·높은·제일"이 있으면 모델이 반대로 말해도 내림차순.
- **우선순위**: 직접 말한 단어(성장·증가, 점포당) > 모델의 해석 > 코드의 알려진 표현 목록 (`CONCEPT_PRIORITY=model_first`). 모델이 시간 안에 못 끝내면 알려진 표현 목록만으로 처리한다.
- 증가율 순위는 **최근 매출 1억 원 미만**인 업종·상권을 뺀다(작은 기준 때문에 증가율이 과장됨). 매출이 없는 그룹(점포 데이터에만 있는 업종)은 순위 대상이 아니다. 제외한 수는 `※`로 알린다.
- 지표: 추정매출, 매출 건수, 주중·주말·성별 매출, **점포 수**(분기 평균), 일반·프랜차이즈 점포 수, 개업·폐업 점포 수, **점포당 월평균 매출**.
- 지역 이름은 별칭도 받는다(여의도, 압구정, 청담, 종로, 영등포, 논현, 독산, 홍대입구, 건대입구, 역삼 …). **노량진**은 1동·2동 중 어느 쪽인지 되묻는다.

### 질문에 없는 조건은 기본값으로 가정하고 답변에 밝힌다
| 빠진 정보 | 기본값 |
|---|---|
| 업종 | 전체 업종 합계 |
| 기간 | 단일 조회·비교·순위·업종 비교 = **최근 4분기**, 추이 = 전체 분기 |
| "최근·요즘", "최근 N년/N분기", "올해", "작년" | **최신 분기** 기준 (C 엔진 `/health`에서 읽음, 못 읽으면 `LATEST_QUARTER`) |
| 증감률의 기준 기간 | 현재 기간 직전의 같은 길이 기간 |
| 순위 개수 | 5개 |

## 질문이 막힐 때: 이유 + 서버가 검증한 제안

HTTP **422** `needs_clarification`. 응답 `detail`:

```json
{
  "error": "needs_clarification",
  "clarification_question": "추천·창업 성공 여부 판단은 지원하지 않습니다. … 이렇게 물어보세요: ① 성수 카페 분기별 매출 추이 보여줘 ② 성수와 홍대의 카페 매출을 비교해줘 ③ 성수 카페 점포당 월평균 매출 알려줘",
  "missing_fields": [],
  "reason": "추천·창업 성공 여부 판단은 지원하지 않습니다. 대신 데이터로 비교해 볼 수 있습니다.",
  "suggested_questions": ["성수 카페 분기별 매출 추이 보여줘", "성수와 홍대의 카페 매출을 비교해줘", "성수 카페 점포당 월평균 매출 알려줘"]
}
```

- `suggested_questions`는 **그대로 다시 보내면 반드시 답이 나온다**. 서버가 모델 없이 규칙만으로 통과하는 것만 남긴다(최대 3개). 질문에 나온 지역·업종을 이어받는다.
- 문구(`clarification_question`)에도 제안이 들어 있어서 A가 `suggested_questions`를 쓰지 않아도 보인다.

| 막힌 이유 | 안내 |
|---|---|
| 추천·창업 판단 | 지원하지 않음 + 같은 지역·업종의 비교 질문 제안 |
| 월별 | 분기 단위 데이터 + "분기별 추이" 제안 |
| 지원하지 않는 비중(예: 카페 점포 비중) | 지원하지 않음 + 가까운 질문 제안 |
| 업종 없이 "어디서 장사하는 게 좋아?" | 업종을 물어봄 + 업종별 예시 질문 |
| 데이터에 없는 항목(유동인구, 임대료, 월세 …) | 없는 항목을 알리고 가능한 질문 제안 |
| 지원 지역 밖(예: 잠실) | 지원 지역 20곳 목록 + 예시 질문 |
| 한 지역만 두고 "비교" | 비교할 지역 제안 |
| 분기 경계가 아닌 기간(2025년 2월) | "2025년 1분기" 제안 |
| 노량진 | 1동·2동 제안 |

## 지금 답할 수 있는 질문 유형 (현재 데이터만)
| 유형 | 예 | 답 |
|---|---|---|
| 입지 | 의류는 어디서 장사하는 게 좋아? | 점포당 월평균 매출 순위(규모·증감 함께) + "추천이 아닌 데이터 순위" 고정 안내 |
| 비중 | 주말·20대·저녁 비중이 높은 곳 | C의 `ratio`(구성비)로 상위 5곳 |
| 분포 | 한강로는 언제 매출이 몰려? / 성수 연령대는? | 한 지역의 시간대·연령·요일·성별 구성비 + 가장 큰 항목 |
| 경쟁 | 카페 경쟁이 심한 곳은? | 점포 수 + 점포당 매출 (공식 과밀지수 아님 안내) |
| 폐업·개업률 | 폐업률 높은 곳은? | 분기 평균 폐업(개업) 수 ÷ 전체 점포 수 |
| 데이터 설명 | 추정매출이 뭐야? / 출처·기준일 | 계산 없이 고정 문구. 응답은 200, `area`는 빈 문자열, `sql`은 빈 문자열 |

`/api/analyze`와 `/api/plan`에서는 `status: "info"`와 `info_text`로 내려간다.

## 점포당 매출 표현 (인식 규칙)
"점포"·"가게"·"매장" 같은 **분모 말**과 "당·별·마다·한 곳당·하나당·대비" 같은 **나누는 말**이 붙어 있으면 점포당 월평균 매출(`per_store`)로 계산한다.

| 표현 예 | 처리 |
|---|---|
| 점포당·가게당·매장당·업소당 매출, 점포별·가게별·매장별 매출, 점포마다 | 점포당 월평균 + 점포 수(근거) |
| 한 곳당·한 집당·가게 하나당·점포 1곳당·1개 점포 매출 | 점포당 월평균 |
| 점포 수 대비 매출, 매출을 점포 수로 나눠줘, 가게 평균 매출 | 점포당 월평균 |
| 점포당 매출과 점포 수 | 점포당 + 점포 수 |
| 점포당 매출 증가율 | 점포당 + 증감률 (증감률은 총매출 기준이라고 안내) |
| 평균 매출, 월평균 매출 | 점포당 월평균 + 합계를 함께, "평균 매출은 점포당 월평균으로 봤다" 안내 |
| 점포당 연매출 | 월평균 값 + "연 환산은 12를 곱하세요" 안내 |
| 객단가 | 지원하지 않음 + 점포당 월평균 매출·결제 건수 제안 |
| 순위 질문(점포별 매출 TOP 5) | 점포당 월평균 기준 정렬, 규모·증감 병기 |

"점포 수 많은 곳", "성수 점포 수"처럼 점포 수만 묻는 질문은 점포당으로 보지 않는다. 모델이 "매출 규모"로 읽어도 질문에 점포당 표현이 있으면 점포당이 기준이다.

## Mock 표시 (실제 분석으로 오인 방지)
- 계산 결과가 Mock이면 `text`가 `[테스트용 Mock 데이터 기반 - 실제 분석 결과가 아닙니다]`로 시작하고, 응답 헤더 `X-Is-Mock: true`, `X-Data-Source: MOCK_TEST_DATA`가 붙는다.
- 본문 필드는 합의된 3개를 유지하기 위해 `is_mock` 필드를 추가하지 않았다.
- `APP_ENV=production`에서는 Mock 모드 자체가 503으로 차단된다.

## 모델이 멈추거나 늦을 때
- 질문 해석(구조화 출력)은 30초·400토큰 안에 끝나야 한다. 넘으면 **모델 없이 서버 규칙**으로 처리한다. 모델이 JSON 형식을 어긴 경우는 502 오류로 알린다.
- 모델 해석(옵션)이 60초를 넘으면 해석 문단만 빠진다. 결론·목록·기준은 코드가 만들므로 항상 나간다.

## 오류 응답 (`detail` 포함)
| 상태 | 상황 |
|---|---|
| 422 `needs_clarification` | 위 표. 계산하지 않으며 본문은 분석 응답이 아님 |
| 422 `plan_validation_failed` | 계획이 데이터셋 규칙 위반 |
| 502 | 모델 출력 스키마 불일치 / 계산 엔진 응답 불일치 / 엔진이 `status=error` (`engine_error` 포함) |
| 503 | Ollama·계산 엔진 연결 불가, Mock 차단 |
| 504 | 계산 엔진 시간 초과 |

## 질문 해석 평가 (`scripts/eval_planner.py`)
```powershell
python scripts/eval_planner.py --rules-only                                   # 모델 없이 규칙만
python scripts/eval_planner.py --model qwen2.5:7b                             # 모델 지정
python scripts/eval_planner.py --model exaone3.5:7.8b --cases scripts/eval_questions_heldout.json
```
- `eval_questions.json`: 52문항(관용 표현 22개 포함). `eval_questions_heldout.json`: 코드의 알려진 표현 목록에 **없는** 말로만 만든 18문항 — 모델이 실제로 이해하는지 본다.
- 결과(2026-11-23, 계획 단계만, 모델 우선):

| 설정 | 기본 52문항 | 처음 본 표현 18문항 |
|---|---|---|
| 개선 전 코드, 규칙만 | 44% | — |
| 개선 전 코드 + llama3.1:8b | 52% | — |
| 규칙만 | 98% | 56% |
| llama3.1:8b | **100%** | 89% |
| qwen2.5:7b | 96% | 89% |
| exaone3.5:7.8b | 96% | **94%** |

- 처음 본 표현 18문항은 문항 수가 적어 모델 간 차이(89~94%)는 오차 범위일 수 있다. 모델을 바꾸려면 `.env`의 `OLLAMA_MODEL`만 바꾸면 된다. exaone은 연구·비상업 라이선스.

## 합의가 필요한 사항 (A ↔ B)
1. **복수 지역·전체**: 지역 비교는 `area`를 쉼표로 잇고, 전체 순위·업종 비교는 `""`. 순위 1위 지역으로 지도 이동 같은 방식을 협의해야 한다.
2. **재질문 표현**: 현재 HTTP 422 + `detail`. `suggested_questions`를 버튼으로 보여 줄지도 협의(선택).
3. **Mock 표시**: 헤더 + `text` 접두 방식. 본문에 `is_mock` 필드 추가 여부.
4. **구조화 표시(선택)**: 지금은 `text`의 줄바꿈만으로 목록이 보인다. 표·카드·막대로 보여 주고 싶으면 응답에 선택 필드(예: 순위 행 배열)를 추가해야 하며, 이는 A와 협의 후 추가한다(`{area, sql, text}`는 유지).
